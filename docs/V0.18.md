# MintCraftOS 0.18.0

## Scope and evidence

Navigation and Combat are enabled again. Browser/CraftTube are unchanged legacy apps;
no HTML5/JavaScript/video work is included. No GPU addon is required.

Target installations: CC:Sable 1.3.4, Avionics 0.6.0, Create: Radars 0.4.9.4,
CC:CBC 1.1.1, CBC 5.11.7. API signatures were checked against installed JAR
method/constants and the following primary source code/documentation:

- [CC:Sable sublevel API](https://techtastic.github.io/CC-Sable/modules/sublevel.html)
- [CC:Sable API and pose wrapper](https://github.com/TechTastic/CC-Sable/tree/master/common/src/main)
- [Avionics source](https://github.com/SolAstrius/CreateAvionics/tree/main/common/src/main/java/ink/astrius/create_avionics/compat/simulated/peripherals)
- [Avionics propeller API and force units](https://github.com/SolAstrius/CreateAvionics/tree/main/common/src/main/java/ink/astrius/create_avionics/compat/aeronautics/peripherals)
- [Avionics native/yielding calls](https://solastrius.github.io/CreateAvionics/guide/mainthread.html)
- [Create: Radars sources](https://github.com/Arsenalists-of-Create/Create-Radar/tree/master/src/main/java/com/happysg/radar/compat/computercraft)
- [CC:CBC API](https://github.com/Drakon7009/CC-CBC)

The source branches are not substitutes for in-game validation of the installed build.
Probe only invokes explicit read allowlists; listing a method does not invoke it.
No actuator is automatically discovered and commanded by guessing method names.

## Commission Navigation

1. Open Navigation / Sensors, select the gimbal, altitude sensor and navigation table. Save.
2. Map each output in Map: unique ID, redstone side or Avionics signal peripheral,
   minimum/maximum, hover neutral, rescue signal and signed mixer coefficients
   for pitch/roll/altitude/heading. Existing Create frequency labels remain in Frequencies.
3. Configure PID gains and output slew limits. Initial gains are zero. Save all configuration
   before starting validation: a mapping/gain/sensor edit invalidates prior confirmation.
4. Optional physical manual inputs are configured under Manual. Touch altitude/yaw controls
   also take priority. Verify directions and behaviour before confirming Manual OK.
5. Test each output individually at a deliberately chosen signal under Calibrate.
   A test lasts 0.3 seconds and requests the mapped rescue values afterwards.
   Acknowledge the test, physically check direction/range, then Verify direction.
6. Establish actual hover and confirm Hover OK. Apply Test rescue, physically verify
   every rescue output and then Rescue OK. A rescue application alone does not validate it.
7. Arm explicitly. Pitch/roll targets become zero; altitude and heading are captured.
   The mixer must have four independent axes, unique endpoints, fresh selected measurements
   and an active sublevel. Six PC sides are only six outputs; use additional supported
   Avionics peripherals when more independent channels are needed.

Manual input suspends the affected controller, clears its integral and captures the new
setpoint on release. Controls never infer that signal zero is an engine stop.
Control is service-owned and permission checked against the running Navigation PID.
Closing/crashing/killing its owner, stale telemetry >0.5s, loss of sublevel or actuator
failure requests rescue. Failsafe must be acknowledged; reboot never rearms.
An interrupted armed session is recorded and requests rescue on the next boot.

**Software-only safety:** rescue can work only while the computer and output hardware
operate. No response is guaranteed on power loss, a completely frozen computer, or a
queued peripheral command whose result is uncertain. Provide independent hardware safety.
Timeouts do not automatically repeat an uncertain control action.

## Commission Combat

1. Connect radar/mount peripherals and Rescan. Devices also offers read-only Probe export
   to `/var/logs/peripheral_probe.log`.
2. Select the radar with Radar; configure its position frame. Use world only when verified;
   body transforms require complete Sable pose (position, quaternion, pivot and scale).
   A recognised Create: Radars fixed-terrain peripheral with no saved frame now uses
   the documented block-position/world convention. Moving sublevels and explicitly saved
   unknown frames still require calibration. Raw position, contact count, rotation, range
   and dish count remain visible when the map cannot be projected; Setup and Read/Probe
   are available directly from the radar toolbar. Missing methods/read failures are shown
   rather than silently dropping a partially supported bearing.
3. Calibrate rotating heading sign/offset and its world/body convention. Set the actual
   cone FOV: this Radar API exposes rotation/range but not FOV, so no measured FOV is invented.
4. Select a mount under Cannons. Configure calibrated muzzle velocity, gravity, yaw/pitch
   signs/offsets, mechanical limits and position/heading frame; confirm and Save.
5. Select a contact by map or Targets. Alias sets a local label, not a recovered player name.
6. Solve displays an **estimated vacuum/no-drag** trajectory, not a complete CBC projectile
   simulation. Missing data, stale contacts, unknown frame or impossible range blocks aiming.
7. Aim once or enable Track (2 Hz). Fire remains separate: one-use confirmation tied to
   the mount/target expires after five seconds. Firing requires an assembled, aligned mount.
   CC:CBC `fire(true)` is released with `fire(false)` after a short pulse; it is never retried.

On timeout the affected cannon is blocked. Physically verify the mount/output state before
using Verify/acknowledge. Tracking stops on errors, target changes or owner closure.
Radar display retains at most 128 contacts and 20 positions per trail. Unchanged `scannedTime`
does not refresh a lost contact; after five seconds it is stale and cannot be commanded.
There are no fabricated player names or Minecraft model silhouettes in the schematic 3D view.

## Architecture and validation

- Inventory: hotplug/Rescan only; flight sensors/control 10 Hz, radar 5 Hz, slow diagnostics 1 Hz.
- Native coroutine workers preserve `task_complete` values, including nil arguments.
- Services cache snapshots; `status()`/`snapshot()` do not acquire peripherals. App drawing
  performs no scan or peripheral call. Independent outputs use `parallel.waitForAll`;
  same-endpoint writes are serialized. Command timeout is 0.5s.
- Graphic geometry/projections are cached by inputs and limited to 5 Hz. Minimized apps
  suspend drawing/snapshot updates; service acquisition and armed control continue.
- Mosaic canvases provide 2x3 subpixels per terminal cell; compositor flushes changed rows
  with `term.blit`. Forms/tabs/toolbars page on narrow screens.
- Config migration retains aircraft/frequency/thrust tables, old profiles and other settings.
  Legacy force tables are explicitly estimates, not measured calibration.

Tests cover Lua syntax, native scheduler arguments, cache/cadence, coordinate rotation,
freshness, PID saturation/wrap/manual priority, calibration gates, owner loss, fire token/pulse
and read-only Probe. CraftOS-PC validation runs in a normal visible window with a disposable
data directory and read-only source mount. It does not touch Minecraft computer saves.
Real addon peripherals and ship flight must still be commissioned progressively in game.
